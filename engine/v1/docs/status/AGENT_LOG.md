# Agent Log

Running log of notable engine-touching work — not custom agents alone. Valid entry
sources are ERA, DRYAD, ARGUS, RIGOR, ED, SAGE, and MAIN (the main/orchestrating
agent acting directly, without spawning a custom agent). SAGE is responsible for
appending an entry here after any of these produces a meaningful finding or change,
including the main agent's own passes. The weekly status task reads this file and
then empties it (back to this header) after summarizing — so entries only need to
cover "since the last weekly report."

## Entry format

`- [YYYY-MM-DD] AGENT: task — outcome (authorized actions taken, if any)`

Examples:

## Log

- [2026-08-31] MAIN: fixed void wall cavity normals — **verified in browser by the author.** `classifyFaces` oriented every triangle toward `meshCenter`, a plain vertex average, which assumes the void is star-shaped about that point. True for a cube or cylinder; false for a bend. `uw-tube-uturn` is a 180° U (six consecutive 30° pitch nodes), so its vertex average sits in the middle of the U, **outside the bore entirely** — triangles on the far leg got "toward `meshCenter`" pointing through the wall and came out inverted. Because [sphereVoidWallTriangleContact](engine/v1/math/Collision.js) is one-sided (`if (DotVector3(triangle.normal, delta) < 0) return NoContact();`), an inverted normal **rejected the player approaching from inside the bore** — they passed straight through. The same normal drives the `normal.y > 0` floor/wall split in `buildVoidCollision`, so some bore floor triangles landed in `wallBounds` and stopped acting as ground. Replaced by `resolveCavitySign`: sample up to 32 strided triangles, probe `centroid + normal · interiorSampleDepth`, ray-parity test with `PointInsideMesh`, take the majority, apply that sign uniformly. Winding is uniform per primitive so one decision serves the whole mesh; per-triangle parity would be O(n²) against ~2000 triangles for a medium-complexity tube.
- [2026-08-31] MAIN: fixed void wall texturing on curved bores — **verified in browser by the author** ("consistent, artifacts subtle, a gigantic improvement"). The non-noise branch built one face group per triangle and planar-projected each along its own dominant axis, so adjacent triangles on a curve chose different axes — hard UV discontinuities, plus stretch up to 1.41× on a cylinder and far worse on a tube. Non-noise void walls now declare `geometry.triplanar` with `material.textureScale: 1` and route through the triplanar shader. **Scale 1 is exact, not approximate:** the planar path maps `uv = (objPos[uAxis], objPos[vAxis])` over the same three axis pairs the shader samples (`objPos.zy` / `.xz` / `.xy`), so an axis-aligned face is unchanged pixel-for-pixel and the 3 axis-aligned cube voids cannot regress.
- [2026-08-31] MAIN: **decision — noise void walls keep per-face baking and are excluded from triplanar. Settled, not deferred.** Terrain/obstacle/water noise bakes a separate texture per coplanar face group (`roleSupportsPerFace` in `NewObject.js` excludes entity parts); triplanar samples one *shared* canvas. Non-entities were deliberately moved **away** from the shared-canvas design because a small shared canvas reads as repetitive tiling and is hard to author against — the per-face design is what buys authorable fine-grain vs large-blotch through `density`/`speckSize`. Routing noise void walls through triplanar would trade that back for the artefacts it replaced. MAIN proposed replacing the per-face branch wholesale and was wrong to; the author supplied the history that settles it.
- [2026-08-31] MAIN: **correction, recorded so it does not propagate.** MAIN asserted mid-pass that "`faceTextureGroups` and triplanar already coexist for entity noise parts, so the combination is safe". **False** — `roleSupportsPerFace` excludes entity parts, so the engine holds two mutually exclusive noise designs and has never combined them. Stated without checking.
- [2026-08-31] MAIN: fixed `offsetAabb` de-instancing in `physics/Collision.js`. It built its result with `AddVector3` (plain vectors) from a `UnitVector3`-backed AABB, while its direct sibling `offsetDetailedBounds` — called on the next line for the same entity — uses `.clone().add(offset)` throughout, as do `computeEntityAabb` and `computeExpandedAabb`. `offsetAabb` was the lone outlier. Surfaced as `aabb.min.clone is not a function` once the new containment test called `getAabbCenter` on its output. MAIN first patched the *consumer* with a plain-arithmetic centre helper, masking the violation at the wrong boundary; the author caught it. Reverted and fixed at the source, so instancing is preserved. Net line change across the regression episode is zero.
- [2026-08-31] MAIN: **finding — face-based noise is face-size dependent; not a void-wall defect.** Noise void walls visibly mismatch the surface they carve into, but the cause is not in the void path: void walls resolve their blueprint from `defaultMesh.detail.texture`, so `density`/`speckSize` are the host's own numbers, and speck size in world units plus density per unit area are both span-independent by construction. The author established that the same configuration looks different depending on face size — short void walls read like the **side** faces of level 1's `ground-main` rather than its **top**. Likely mechanism, unconfirmed: speck placement is `Math.random()` per speck with count scaling by canvas area, so a large face averages out smooth while a small one carries large relative variance, with integer quantisation compounding it at small sizes. Void walls only made an existing seam visible. Not a deferral — a solution is already drafted outside this pass, awaiting the author's review.

- [2026-08-30] MAIN: proposed removing the `voidWallMeshes` stencil write from `drawVoidStencil` ([Render.js](engine/v1/handlers/Render.js)) as redundant now that exact open-face clipping ships (CNE 0.28.2) — **retracted, no code changed**. The user identified it as the cause of a camera-in-void bug already fixed in CNE 0.29.1. Mechanism: the stencil mask is screen-space, so with the camera inside a void the opening can fall entirely outside the frustum; with open faces as the only mask writer the mask is empty, void walls drawn under `stencilIncludeBit` are rejected everywhere, and the player sees solid terrain from inside the bore. The reason is recorded at the call site. The original analysis reasoned from a single viewpoint (looking down into a bore from above the deck, where the wall silhouette is only a thin ring) and never considered the camera being inside the void volume. General lesson: "exact geometry makes the other writer unnecessary" is an object-space claim and does not transfer to a screen-space mask. The approved plan file carries a do-not-do block so the recommendation cannot be picked back up.
- [2026-08-30] MAIN: aggregated void classification logging in [NewVoid.js](engine/v1/builder/NewVoid.js) — the per-void `Void classified:` line fired once per void, producing 38+ consecutive console lines on lvl2 and slowing the browser. Replaced with a `totals` accumulator threaded through both builders and one summary line in `BuildVoidWalls`. `node --check` passes; not yet exercised in the browser.
- [2026-08-30] MAIN: diagnosed and fixed void collision suppression — three tube voids in lvl2 could not be entered, and some swiss-cheese cylinder holes failed to suppress. **Two defects, one root cause: the suppression tests asked an overlap question against an *approximation* of the void rather than asking whether the body is inside it.** (a) [isVoidCancelled](engine/v1/physics/Collision.js#L505) and [IsPointInSuppressingVoid](engine/v1/physics/Collision.js#L526) gate on `NarrowphaseTest(bounds, ns.detailedBounds)`; a `tube` void resolves to `triangle-soup`, and `sphereTriangleContact` returns `NoContact` once `distSq > radius²` — proximity, not containment. Suppression therefore held only in a thin shell hugging the bore wall: half-in was suppressed, fully-in was not, host collision re-applied and ejected the player, back at the rim they were suppressed again. That oscillation is why the tubes were unenterable. (b) `cylinder` voids resolve to `capsule`, and `computeCapsuleFromMesh` gives `radius = max(dim.x,dim.z)/2`, `halfHeight = max(0, dim.y/2 − radius)`. A capsule's hemispherical caps under-cover the true cylinder near top and bottom, tapering to a point at the exact deck surface — where a player at a hole rim most needs suppressing. It also clamps: 10 of the 27 swiss holes are wider than tall, so `halfHeight` hits 0 and they degenerate to spheres. Wide holes bulge past the slab and suppress reliably; narrow holes keep a real capsule whose taper leaves an uncovered ring at deck level — matching the report that most holes work but small ones fail. **Fix:** persist each void's world triangles as `solidTriangles` and fall back to `PointInsideMesh` ray-parity containment when narrowphase misses. Cheap path first; containment added as an OR so suppression can only widen, meaning no currently-working case can regress. Ray parity is valid over a union of disjoint closed meshes, which is why concatenating obstacle void parts into one soup works. No defensive check needed — `BuildVoidWalls` is called unconditionally from `NewLevel.js:322` and both builders assign the field to every entry they iterate. Side effect: [Camera.js:374](engine/v1/handlers/game/Camera.js#L374) also calls `IsPointInSuppressingVoid`, so camera obstruction inherits the correction. `node --check` passes; **not yet verified in the browser.** Residual accepted by decision, not deferred: degenerate capsule bounds still *over*-suppress (`swiss-central-void` presents as a sphere of radius 42 clipped by its 84×10×84 AABB, so box corners outside the true cylinder are suppressed). Not a reported symptom, and switching to containment-only would risk regressing bodies straddling a void boundary.
- [2026-08-30] MAIN: diagnosed the void stencil bug — **no code changed.** All non-void geometry disappears when the camera is inside a bore. [drawVoidStencil](engine/v1/handlers/Render.js#L1987) uses `stencilFunc(ALWAYS)` with `stencilOp(KEEP, KEEP, REPLACE)`, so `REPLACE` fires wherever the *depth* test passes, and depth is `LEQUAL` against a pre-pass primed from all terrain. A void face therefore sets the type bit wherever it is at-or-in-front-of the nearest host, and that bit excludes every host at that pixel **at any depth behind it** — the mask is a flat 2D screen-space punch with no depth bound. Pre-existing and unrelated to open-face clipping; `level0/stage0` has one terrain void and shows it. Entities are immune because `Render.js:2128` draws them with no stencil option at all. Obstacles are unaffected only because there are **zero obstacle voids in the entire project** (`levels.json` 1 terrain / 0 obstacle, `lvl2.json` 38 / 0), so bit `0x02` is never written — authoring one obstacle void would break obstacles identically. Fix direction is stencil volume counting (front faces increment, back faces decrement) to bound the punch to the void solid; blocker is that the engine never enables `gl.CULL_FACE` anywhere, so it needs culling or `stencilOpSeparate`. Left for its own design pass.
