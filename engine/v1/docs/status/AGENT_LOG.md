- [2026-09-07] MAIN: **implemented the author's chosen fix for noise void-wall linings — one shared tiling canvas, still on the planar path.** After the rejected triplanar attempt above, four options were put to the author and they picked "shared canvas + resolution floor", under the standing constraint that **no option uses triplanar**.
  **Two renderer facts constrained the design and were checked before writing anything:** `Render.js` binds any textureID containing `::face=` as `CLAMP_TO_EDGE` rather than `REPEAT`, so a per-face bake *can never tile*; and the `material.textureScale` uniform is applied **only** on the triplanar path. Together those force a shared canvas to be an ordinary tiling surface id with the tile scale carried in the UVs themselves.
  So the noise branch now calls `GenerateFaceProjectedUvs` with `normalize` **false** — raw planar UVs on each group's dominant axis instead of per-face `[0,1]` — and multiplies them by `textureScale / textureBlueprint.size`. **Why that factor:** a tile covers `size / textureScale` CNU, so stone-block's 64 against lvl2's `textureScale` 2 gives one tile per 32 CNU = 2 px per CNU — *exactly* the texel density the host's own face bakes get, since those are sized `span * textureScale` with normalized UVs. The lining's noise therefore matches the host wall's scale. **This is also why the naive reading of "shared canvas" was wrong:** keeping normalized `[0,1]` UVs and merely forcing a uniform canvas size would stretch the whole image across a tiny facet, so speck scale would vary with facet size. `groupCoplanarPieces` is retained — the per-group dominant-axis choice still drives the projection.

- [2026-09-07] MAIN: **diagnosed the author-reported void edge collision bug — root cause found, deliberately NOT fixed — and made two smaller collision changes that were measured and kept.**
  **The reported bug.** Hitting a regular object ~20% above the bottom of the player's bounds gives a net upward launch as horizontal momentum becomes partly vertical; the same against a void edge halts you in place and sometimes teleports your whole bounds into the void's XZ. The author recalled that void collision *skips a step* regular collision does, and that is exactly right. [`resolveAabbDetailedPushContact`](engine/v1/physics/Collision.js) guards `candidateBounds.type !== "triangle-soup"` and then calls `narrowphaseContact` with an AABB built from the entity. For an obb/aabb candidate that runs `AabbObbContact`, a SAT test returning the **minimum penetration axis** — so clipping a low ledge yields a vertical `pushNormal` and `pushDepth` lifts the body over it. **That is the launch.** A `voidWall` is not `"triangle-soup"`, so it enters that branch — but `narrowphaseContact` dispatches on `type.substring(0,2)` pairs, giving `"aa"+"vo"` = `"aavo"`, and **no `aavo` case exists** (only `spvo`, `vosp`, `cavo`, `voca` — sphere and capsule). It silently returns `NoContact()` and falls to `projectAabbPushContact`, which produces **both** symptoms: the push uses the raw one-sided **triangle** normal, horizontal on a cavity wall, so there is no vertical component to redirect momentum into (halted in place); and depth is `dot(contactPoint − entityAabbExtremeCorner, normal)`, the AABB's far corner projected onto a single triangle's plane, over-estimating penetration by up to a full body extent and pushing the body that far along the triangle normal (teleported into the void's XZ). **Corroboration this is an oversight, not design:** `resolvePushSupportPoint` explicitly pairs `"triangle-soup"` and `"voidWall"`, so it knows linings take the projection path, while `resolveAabbDetailedPushContact` names only triangle-soup. Fixing it needs an AABB-vs-void-wall narrowphase giving a min-penetration push — new math in `math/Collision.js` plus wiring — and carries a real design choice (min-penetration against a local triangle cluster vs treating the lining region as a convex hull), so it was left for the author to direct. **Nothing was changed for it.**
  **Two false starts, recorded because both fixed things the author never reported.** In the author's words: *"whatever you fixed, I have no clue what the effect is, as it was not part of the report."* Also recorded from the author: **slope correction has been broken for months**, so the cave tunnel's non-flat floor cannot be used to test ground contact at all — an entire tunnel-based test battery was invalid for that reason and was abandoned on instruction. It now blocks, while the aperture still passes, with the open→blocked crossover landing exactly on the measured bore edge at z 636.
  **Change 2, kept — and its value is entity-side, not the player's.** `ResolveCollisions` computed `isSurfaceCandidate` from `type`, excluding `voidWall`, so a lining could never build a ground or wall contact; and `buildGroundContact` stamped the raw type, so even if built it would have been typed `"voidWall"` and rejected by `ApplySurfaceCorrection` and `ApplyGroundSnap`, which both gate on terrain-or-obstacle. That contradicted `ProbeGroundContact`, which deliberately reports lining floors under their **source category** — *"Void-wall floors (upward normal) are standable ground; reported under their source category"* — precisely so those gates pass. **Scope note:** this is inert for the player, because [Master.js:130](engine/v1/physics/Master.js#L130) overwrites the resolver's `groundContact` with `ProbeGroundContact` every iteration — but that call sits inside `if (isPlayer)`, so **non-player entities take the resolver's contact as their only source.** This change is what lets an entity be grounded on a void wall floor at all.
  **Cost, since the author asked whether change 1 was cheap enough to keep.** Per call, `PointInsideMesh` costs 0.1–0.2 µs on the box/capsule/sphere voids that make up most of lvl2 against 0.33–0.4 µs for the `NarrowphaseTest` it replaces, but 11–29 µs on the three large triangle-soup tube voids (1172–2324 tris) against 5–10 µs. Worst case is ~52 µs for the whole function against a 16,667 µs frame budget (~0.3%), and that is the entire function rather than the delta. Change 2 costs one property copy per contact and one `||` per resolved collision.

- [2026-09-08] DRYAD: **one applied finding on the new narrowphase — anti-parallel axis collapse.** The dedup used a plain dot against `axisDuplicateDot`, treating an axis and its negation as distinct, so on closed soups (cone, tube, torus) opposing faces kept near-duplicate axes and each cost a full extra pass over the cluster. Swapped to `Math.abs`.
