# Deferred Work

Explicitly deferred implementations or decisions — work that was started, considered,
or raised during a task and consciously postponed, along with who deferred it and why.

This is NOT the idea backlog (see `engine/v1/docs/todo` for that). Entries here should
only be things that came up mid-task and got pushed off, not general feature ideas.

Entries persist across weekly reports until resolved, then they are **deleted** —
not checked off, not annotated as done. SAGE sweeps this list on every `log` call
and removes what the pass resolved; any other agent may delete a resolved entry too.

## Entry format

`- [ ] [YYYY-MM-DD] Item — deferred by WHO, because REASON`

Example:

`- [ ] [2026-07-09] Camera.js CNU_SCALE calibration — deferred by ED, because it depends on render pipeline stabilizing first (see CNU_VS_WORLDUNITS.md Section 4)`

- [ ] [2026-08-05] Translucent terrain and obstacles still depth-reject one another — deferred by main agent, because routing them through the new entity-style translucent pass would break void-wall stencil occlusion. [`drawDepthPrePass`](engine/v1/handlers/Render.js#L1655) primes the void stencil from terrain and obstacles, and relies on full depth-write from that same geometry; making those meshes skip depth-write in the main pass would leave the two paths disagreeing. Terrain and obstacles also draw under `stencilExcludeBit` 0x01/0x02 filters, which a single globally-sorted translucent list cannot preserve. The real fix is teaching the depth-prepass/stencil system to distinguish translucent terrain/obstacles from the entity translucent pass — a dedicated follow-up, because it reaches into the nullSpace/void-wall system.
- [ ] [2026-08-05] Translucent sorting is per-object, not per-fragment — deferred by main agent, because a correct fix is a different technique entirely (weighted-blended OIT or depth peeling), not an increment on this pass. Three consequences share this root: two intersecting translucent meshes pop when their centroid order flips; a mesh straddling the water surface is bucketed whole by its origin's `y` ([Render.js:1355](engine/v1/handlers/Render.js#L1355)); and parts of one entity that are translucent no longer occlude one another. All are negligible at particle scale and would matter for large intersecting translucent geometry or a heavily self-overlapping translucent model.
- [ ] [2026-08-05] Decals on a translucent entity part now draw underneath it — deferred by main agent, because the fix is a render-pipeline restructure rather than a local change: the decal pass would have to be split so a translucent part's decals draw with the part in PASS D instead of wholesale in PASS E, which means resolving decal ordering against the same depth-write-free sort the parts use. Introduced by this pass. `drawDecalPass` ([Render.js:1463](engine/v1/handlers/Render.js#L1463)) runs at PASS E and walks all entity parts regardless of bucket, drawing with `depthMask(false)`; translucent parts moved from PASS A (before decals) to PASS D (after), so such a part now blends over its own decal. Previously correct in both directions.
- [ ] [2026-08-04] Particle generators on animated entity parts do not follow the animation — deferred by main agent, because fixing it means deciding whether generators should track the display pose or the true pose, a design question outside this pass. [`targetTransform`](engine/v1/handlers/game/Level.js#L422) resolves an entity part to `part.mesh.transform`, which [`applyModelPose`](engine/v1/builder/NewEntity.js#L339) writes from the *true* hierarchy pose; `ResolveEntityAnimation` writes only `displayTransform`/`displayColor` ([Animation.js:153](engine/v1/handlers/game/Animation.js#L153)) alongside it. `mesh.transform` therefore never carries animation, so a generator on a part that swings through one stays put. Engine-wide, not Simulator-specific — merely first visible in the Simulator, the one place an idle model animates in isolation.
