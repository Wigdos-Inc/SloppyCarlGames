# player/ — Player Character

## Responsibility
Owns all player state, movement logic, model assembly, abilities, and animation. `Master.js` is the central orchestrator; `Model.js` assembles the player as an entity via the shared builder. Handlers call into `Master.js` to drive per-frame updates; physics calls the shared `builder/NewEntity.js` model-sync function directly to re-pose the player after physics resolution, the same as any other entity.

## Files
- `Master.js` — Player state orchestrator. Extends a builder-assembled entity into player state via `createDefaultPlayerState` (adds action/movement/ability/checkpoint fields on top of the built entity; widens `collision.simRadiusPadding` to 24 since the player broadphases a larger radius than the entity default). Exports `InitializePlayer`, `UpdatePlayer`, `UpdatePlayerModel`, `ResolvePlayerState`, `SetPlayerAction`, `TriggerPlayerDeath`, `TriggerPlayerRespawnSequence`, `RespawnPlayer`, `GetPlayerState`, `GetPlayerInput`, and `PlayerAPI` (the `ENGINE.Level.Player` public surface). `SetPlayerAction` is the sole write path for `playerState.action` — it sets `action`/`previousAction`, logs the transition, and conditionally fires `PLAYER_ACTION_CHANGE`; all transition sites (`ResolvePlayerState`, `TriggerPlayerDeath`, `RespawnPlayer`, jump/stun triggers elsewhere) go through it rather than writing `action` directly. `createDefaultPlayerState` also scales the builder's default `modelTurnRate` per medium — `air` by `character.meta.airControl`, `water` by `underwaterAirControl` — so a floatier character's model leans as loosely as it steers.

  **`ResolvePlayerState`'s branch order is the state machine's priority.** `Sliding` sits at the top, keyed on `surfaceContact === "sliding"` and with **no exit rule of its own** — it holds for exactly as long as the probe reports a sliding contact, and the classifier's `Recover` hysteresis (see physics.md) is what ends it. Below it come underwater (`Floating`/`Sinking`), airborne (`Jumping`/`Falling`), then the grounded set (`Stopping`/`Running`/`Idle`).

  **Teleports snap, they do not ease.** `snapOrientationUpright` resets `alignedUp` and `referenceNormal` to world up, zeroes pitch and roll on `transform.rotation` (keeping yaw), and clears `animationRuntime` outright — dropping the model pose so it re-seeds upright at the destination instead of easing in from the surface the player left. `RespawnPlayer` calls it, then reseeds `facing` from the respawn rotation and replaces `inputFrame` wholesale, so no carried tangent survives the teleport.
- `Movement.js` — Per-frame movement handler. Translates input flags into velocity deltas; it never writes position. `UpdateMovement` works in a **surface-relative frame**, not world XZ: velocity is split against `playerState.alignedUp` into `normalVelocity = up · dot(velocity, up)` and a tangent remainder `tVel`, acceleration/deceleration/clamping all run on `tVel`, and the two recombine at the end with the normal component preserved untouched.

  **The carried tangent frame.** `getMovementDirection` does not flatten the camera basis and project it — it reads `playerState.inputFrame`, a per-entity frame carrying `carriedForward`, `previousCameraYaw`, `previousHasInput` and `previousGrounded`. `advanceCarriedForward` composes the frame-to-frame camera yaw delta onto `carriedForward` and re-projects onto the current surface plane, and **reseeds from the camera** on three transitions: a no-input→input press, a change in `grounded`, and a collapse of the transported vector below `minTangent` (0.05). The seed is `ProjectOntoPlane(camFwd, up)` plus an uphill term weighted by `(1 − |up.y|) · −dot(camFwd, up)` — so pressing forward while the camera faces into a slope aims up it rather than into it. The camera forward is passed through `ResolveVector3Axis` at its hoist site, so it is unit length rather than carrying `cos(pitch)`, and `cameraYaw = atan2(camFwd.x, camFwd.z)` derives from it; both are hoisted above the input test so the yaw stays current through input-less frames. `direction` — the XZ shadow of `tangentDirection` — exists only for the flat latch checks (`stoppingActive`, `getPrimaryOppositeHeld`, reverse-intent), which are threshold tests in the flat frame. The three `previous*` fields are written unconditionally at the end of the function.

  **Support and slide damping.** `support = max(|up.y|, minSupport)` — cos(incline) floored at 0.25, engaging past 75.5° so no ordinary slope reaches it — scales both `ApplyDeceleration` call sites, so friction falls off with steepness while a wall still brakes and an overhang cannot accelerate. On a sliding contact, input whose component along the downslope direction (`ProjectOntoPlane(WORLD_NORMALS.Down, up)`, left un-normalized) is negative has its acceleration scaled by 0.15 — uphill input is damped, downhill is not.

  **Jump and facing.** The jump gate accepts `grounded || onSlidingSurface`, launches **along the surface normal** (`velocity.set(tVel + up · launchSpeed)`) with `solveJumpLaunchVelocity`'s result halved on a slide, and writes `jumpStartY`/`jumpApexY` before `SetPlayerAction("Jumping")`. `turnFacingToward` rate-limits `playerState.facing` toward the surface-tangential velocity direction at `meta.momentumTurnRate`, via `RotateTowardVector3` on the plane-projected facing; a facing that has collapsed onto the new normal snaps to the target rather than limiting against an angle that no longer exists. Nothing here writes `transform.rotation` — `facing` is the heading, and `physics/Correction.js` solves the rotation from it.
- `Model.js` — Player entity assembler. `synthesizeDefinition` builds a standard entity-definition object from a `characters.json` template plus level-supplied placement data (spawn position, scale, animations, custom events); `BuildPlayerModel` passes it to `builder/NewEntity.js`'s `BuildEntity` with `textureScale: null` (opts the player out of the shared entity-part geometry/face-texture cache, matching the model's historical inline build path) and a dedicated zero-origin `playerSurfaceMap` (spawn position is absolute, so the surface origin is `(0,0,0)`). `RefreshPlayerModel` calls the shared `UpdateEntityModelFromTransform` to re-pose and recompute `collision.aabb`/`physics`/`hurtbox`/`hitbox` each frame. `filterDeadDecals` drops image decals that failed to load by shallow-copying only the affected part, so the shared `characters.json` template is never mutated. `characters.json` bypasses `core/normalize.js`; its Unit-instancing (parts' `dimensions`/`localPosition`/`localRotation`/`pivot`, decal transforms, and tube `primitiveOptions` node fields) happens once at boot in `builder/templates/Instance.js`'s `instanceCharacterTemplates`, called from `core/ini.js` before any engine module reads the template. `Model.js` keeps its own `characters.json` import for call-time reads only — it no longer instances anything itself. Exports `CharacterData`, `BuildPlayerModel`, `RefreshPlayerModel`.
- `Abilities.js` — Player ability definitions (jump, boost, etc.) and application logic. Accepts ability handler callbacks from game code.
- `Animation.js` — Player-specific animation handler. Drives visual state transitions based on player movement and action state.
- `characters.json` — Character preset definitions, one per playable character (including `carl`). Each entry supplies a `model.parts` list (standard entity part shape, including `tube` parts) and a `collisionOverride` consumed the same way as an entity's. Raw numeric values are instanced into `Unit`/`UnitVector3` by `Model.js`'s IIFE at module load; downstream code receives pre-instanced values.

## Boundaries
**Called by:** `handlers/game/Level.js` (`InitializePlayer`, `UpdatePlayer`, `ResolvePlayerState`, `GetPlayerState`); `physics/Master.js` (`TriggerPlayerRespawnSequence` only — model sync goes through `builder/NewEntity.js`'s `UpdateEntityModelFromTransform`, not a player-specific function).  
**Calls into:** `builder/NewEntity.js` (`BuildEntity`, `UpdateEntityModelFromTransform` — the player is built and re-posed by the same code path as any other entity); `math/` (Utilities, Vector3); `core/` (meta, config, normalize).  
**Does not:** Manage its own update loop; drive rendering directly (model updates are consumed by `Render.js`); apply physics forces (those are applied by `physics/Master.js`); build its own geometry/collision math (delegated to `builder/NewEntity.js`).

## Invariants
- There is one player state object in the engine at a time, held in `Master.js`.
- `playerInputFlags` is written by game code each frame via `ENGINE.Level.Player.Input` and read by the player update each frame.
- `characters.json` values are instanced once at boot by `builder/templates/Instance.js` (called from `core/ini.js`), before any engine module reads the template. No downstream code re-instances them.
- The player carries no bespoke collision system — `collision.aabb`/`physics`/`hurtbox`/`hitbox` are the same builder-computed structure every entity has, recomputed each frame by `UpdateEntityModelFromTransform`. There is no separate `collision.profile` cache.
- `playerState.action` is written only through `SetPlayerAction`; no other module assigns `playerState.action` directly.
- `Movement.js` owns `facing` and `inputFrame`; `physics/Correction.js` reads `facing` and writes `transform.rotation`. Neither writes the other's field — movement produces a heading, physics produces an orientation, and the split is what keeps the collider's rotation exact while the heading is rate-limited.
- Movement is computed in the plane of `alignedUp`, not world XZ. The flat frame survives only where a threshold is genuinely flat — the stopping/reverse-intent latches and the camera-relative opposite-held test — and those read an explicit XZ shadow rather than the real velocity.
