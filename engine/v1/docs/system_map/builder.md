# builder/ — Scene and Asset Construction

## Responsibility
Constructs all visual and structural scene data: 3D WebGL meshes, entity models, obstacles, terrain, null-space void walls, procedural textures, scatter details, UI element trees, and the full level scene graph. Builders are called by handlers (and in one case by physics), produce output objects, and return. They hold no persistent state and drive no update loops.

## Files
- `NewLevel.js` — Level scene graph assembler. `BuildLevel` is the primary entry point. Orchestrates all other builders to produce the complete `sceneGraph` object consumed by the renderer and physics pipeline. Also exports `RefreshSceneBoundingBoxes`.
- `NewObject.js` — Primitive 3D mesh builder. Generates WebGL geometry (positions, normals, UVs, indices) for mesh primitives. Foundation for all other geometry builders. Entity-part builds (role `"entity-part"`, `textureScale !== null`) are memoized: `buildEntityPartGeometryTemplate` constructs and freezes an immutable `{ positions, indices, uvs, bounds, faceTextureGroups?, triplanar? }` template once per `blueprintId::partId` key, stored in a caller-supplied `geometryCache` Map and shared by reference across all same-blueprint instances; per-instance state (transform, material, worldAabb, detailedBounds, scatter, customTextures) is always built fresh. `textureScale: null` signals the player-model inline build path, which bypasses caching entirely. Noise-pattern entity parts set `template.triplanar = true` and skip both `faceTextureGroups` construction and UV frequency-scaling (UVs are left at their default values — unused by the triplanar shader but kept valid so the shared VAO uv-buffer layout is unchanged); `BuildObject` sets `material.textureScale` per-mesh for triplanar parts so density stays correct across geometry shared by same-blueprint instances. Sphere UVs for non-triplanar entity-parts are pre-scaled by physical span (U → π·dimensions.x, V → π·dimensions.y·0.5) before frequency UV scaling so textures read at a consistent world scale regardless of part radius. `buildSphere`/`buildCylinder`/`buildCapsule`'s surface parameterizations are mirrored by `Render.js`'s decal `projectToSurface` GLSL for curved-surface decal conforming — the two must stay in sync if either changes. The `tube` shape is a **node-chain bone walk** rather than a single extrusion: `resolveTubeNodes` starts at an identity root frame (carrying the part's own `size`/`thickness`/`curved`/`smoothness`) and composes each `primitiveOptions.nodes[]` entry onto the running frame, so a node's `localPosition` is applied in the previous node's rotated axes. `makeTubeNode` extracts each node's `center` (frame translation) plus its `forward` (frame Y axis), `xAxis` and `zAxis`. `buildTube` lays one hollow ring cross-section at every node (`appendTubeRing`), then walks consecutive pairs: if `nodeA.curved`, it samples a connector centerline via `SampleConnectorCenterline` and lofts intermediate rings along `ParallelTransportFrames`, linearly interpolating `radiusX`/`radiusZ`/`thickness` across the span; `orientConnectorFrames` then distributes a residual roll so the final frame's normal lands on `nodeB`'s authored `xAxis`, giving a seamless join. Rings are stitched pairwise (`stitchTubeRings`), the two chain ends are closed (`capTubeRing`), and per-connector face groups are emitted as angular sectors with radial normals (`appendTubeConnectorFaceGroups`), mirroring `buildTorus` rather than the outer/inner/top/bottom split that has no meaning for a multi-node tube. Exports `GenerateUVs` and `TransformPointByMatrix` (used by `NewVoid.js`).
- `NewEntity.js` — Generic animated entity builder, shared by both non-player entities and the player (see `player/Model.js`). `BuildEntity(definition, surfaceMap, textureScale, faceTextureStore, geometryCache)` first resolves `definition` through `NewTemplate.js`'s `ResolveEntitySource` (a no-op for non-template definitions), then constructs a multi-part entity model with collision profile and returns `{ entity }`. `buildModel`'s part index and parent→child links are built in two passes (index first, then children arrays), so `definition.model.parts` may declare a child before its parent — part order is unconstrained. Face textures generated during the build write directly into the caller-supplied `faceTextureStore` (no separate return). `computeDetailedBoundsForEntity` resolves the three-layer collision (`physics`/`hurtbox`/`hitbox`) from `collisionOverride`; a `collisionOverride.physics` value of `"auto"` is resolved by `resolvePhysicsShape` at build time to `"capsule"` when the AABB is taller than it is wide/deep, else `"sphere"` — this needs the built AABB, so it cannot happen earlier in `core/normalize.js`. `computeSphereFromAabb` returns the **inscribed** sphere (`radius = min(halfX, halfY, halfZ)`), not the circumscribing half-diagonal, so a sphere collider never extends past the model's AABB on any axis. After the initial `applyModelPose`, `buildModel` grounds the whole model on the spawn surface rather than just the root part's bottom face: it captures `groundPlaneY` (the pre-correction `rootTransform.position.y`), computes `computeEntityAabb(model)`, translates `rootTransform.position.y` by `groundPlaneY - aabb.min.y`, then re-poses so `defaultPose` snapshots the grounded result. Entities whose root part is already the model's lowest point get a zero delta (identical to the assembly-time per-root grounding, which is kept as the baseline). Exports `UpdateEntityModelFromTransform` for post-physics model synchronization (used for the player and all non-player entities alike) and `ComputeCapsuleFromAabb` (used by `physics/Collision.js`'s ground-contact probe).
- `NewObstacle.js` — Obstacle mesh builder. `BuildObstacle(source, index, options)` first resolves `source` through `NewTemplate.js`'s `ResolveObjectSource(source, "obstacle")` (a no-op for non-template definitions — same reference returned), then builds obstacle geometry for scene placement; `options` carries `{ textureScale, faceTextureStore }` so per-face generated textures write into the same content-addressed store as terrain. `BuildObstacles(source, options)` maps `BuildObstacle` over a definition list. Each obstacle record carries a `worldAabb`. Exports `MergeAabb` (the multi-part AABB-union helper used internally to build a record's `worldAabb`) and `CreateDetailedBoundsFromParts` for reuse by external callers that reposition an already-built obstacle's parts — currently `handlers/game/Simulator.js`, after it re-seats a loaded obstacle onto the preview platform.
- `NewTexture.js` — Procedural 2D texture generator and visual resource manager. Five patterns: `noise`, `tiles`, `stripes`, `grid`, `radial`. Three element shapes for noise/tiles/grid cells: `circle`, `diamond`, square (default). **Frequency patterns** (`tiles`, `stripes`, `grid`) carry their spatial frequency in per-mesh UV tiling and do not bake `density` into the shared canvas — only `speckSize` is applied. **Non-frequency patterns** (`noise`, `radial`) bake `density` into the canvas directly. Per-face **face textures** (noise only, non-square canvas sized to face UV span in pixels) are **content-addressed**: `buildFaceTextureSignature` produces a deterministic key from the base texture id, resolved density/speckSize/shape/colors, face pixel size, and animation params; identical content shares one baked canvas and one GL texture. `BuildFaceTextureData(store, ...)` takes a content-addressed store as its first argument, dedups via the internal `getOrBuildFaceTexture` gate, and returns only `{ faceTextureGroups }`. `ResolveNoiseFaceBlueprint(textureBlueprint, textureDetail)` is the shared helper that composes density/speckSize, applies the detail shape, and applies conditional `primary`/`secondary` rgba color overrides for per-face noise baking — called by both the mesh per-face path and `NewVoid.js`. `ComputeGeneratedTextureID(generatedTexture)` derives a color-override-aware texture id (appending `p=` and `s=` rgba segments when overrides are present). `RgbaToHex` converts an rgba object to a hex string. Canvas-level `primary`/`secondary` rgba overrides replace template default colors at bake time; the shader tint for generated textures is neutral `{1,1,1,1}`. Each texture registry entry holds `{ id, definition, source (canvas), dirty }`. Entries with `definition.animation.able === true` are picked up by `handlers/game/Texture.js` for hold/blend animation; `definition.isFaceTexture` flags the rebuild path. `BuildNoiseAnimationOptions` derives animation config from a blueprint + textureDetail pair. `collectCustomTextures` walks a mesh/part's authored decal entries into a flat `customTextureUsage` list (carrying `opacity` for image entries) for registry construction. Image-type decals with `opacity < 1` are baked once at registry build time: `bakeImageDecalOpacity` composites the raw bitmap onto a straight-alpha 2D canvas via `globalAlpha`; `opacity >= 1` skips baking and uses the raw bitmap directly (fast path). `createTextureRegistry`'s custom-texture loop invokes this bake per image decal; shape decals and the render-time tint path are unaffected. `AddToVisualResources` incrementally registers textures for objects spawned mid-session. Exports `PrepareLevelVisualResources`, `AddToVisualResources`, `BuildTextureSurface`, `BuildNoiseFaceCanvas`, `BuildFaceTextureData`, `ResolveNoiseFaceBlueprint`, `BuildNoiseAnimationOptions`, `FREQUENCY_PATTERN_CONFIG`, `VISUAL_TEMPLATES`, `ComputeGeneratedTextureID`, `RgbaToHex`.
- `NewScatter.js` — Procedurally generated multi-part static scatter objects placed on terrain surfaces. Each object's open faces (from null-space relations, see `NewVoid.js`) are threaded through to `iterateScatterInstances`, which rejects any sample whose XZ footprint AABB overlaps a top-relevant open face's XZ AABB (conservative AABB-vs-AABB, reusing the footprint math shared with the parent-bounds check) so scatter is not generated over openings. Only root parts (`level === 0`) are footprint-checked.
- `NewParticles.js` — Particle group generator **and** the per-group runtime lifetime classes. `GenerateParticles(request, viewerPosition, textureScale, faceTextureStore, geometryCache)` takes `request = { templateId, position (UnitVector3 cnu), overrides, mode, target }` and returns `{ groups }` — built entities, one per group. Two generation gates run first: `performanceParticleMultiplier()` reads `CONFIG.PERFORMANCE.Particles` with the same `High → 1 / Low → 0 / else 0.5` shape as `GetPerformanceScatterMultiplier` (Low additionally warn-logs and blocks outright, and the multiplier is applied to `count` via `Math.max(1, Math.round(...))`), then `IsBeyondSimDistance(viewerPosition, request.position)` from `physics/Collision.js` skips generation outside simulation range. `viewerPosition` is a parameter rather than a request field because the request is stored on the group for reseeding and a captured position would be stale; build-time callers pass `payload.player.spawnPosition` (no camera exists yet during `BuildLevel`), the runtime seeding path passes the live camera position. Resolution (`resolveRequest`) uses null-sentinel precedence over six overridable keys — `count`, `spread`, `physics`, `color`, `velocity`, `duration`; `part` and `amount` are template-owned. A **partial** `overrides` object is valid and needs no padding: every override key is `isExpected: false` with a `null` fallback, so `resolveFieldLayer` fills the omitted ones silently and `pick` falls through to the template for exactly those. Group sizing is tiered by particle count: `< 3` produces N single-part groups, `3–7` produces three near-equal groups (`balancedSplit`), and `>= 8` samples a group count in `[max(3, ceil(N/5)), floor(N/2)]` and jitters the even split with ±1 transfers that keep every group within 2–5 parts — combinations are *sampled, never enumerated*, since partitions of N into {2,3,4,5} grow ≈ N⁴/2880. `groupLayouts` holds 1–5-part offset tables as **dimensionless multipliers of the part's own dimensions** (raw ratios, deliberately never Unit-instanced), so spacing stays proportional at any particle size. Each group's velocity is the template vector scaled 0.8–1.2× and perturbed inside a spread cone (`randomInCone`; 10°/30°/60° for `narrow`/`medium`/`wide`, and 180° for `max`, which is a full sphere rather than a cone) and is live on `entity.velocity` for all three physics modes. Because that sample is drawn **once per group**, the number of distinct trajectories in a burst is the group count, not the particle count — an all-directions effect comes from `max` plus a high `count`, never from per-particle velocity, which is rejected by design since a group's parts must hold a rigid formation. Per-particle colour is written to `part.mesh.displayColor` by `writeParticleRgb(startColor, endColor, decayFactor, offset, target)` — `Clamp01(Lerp(start, end, factor) + offset)` per channel, writing into a supplied target so build allocates once and recycle mutates in place — never into `texture.generated.primary`. `offset` is **one** shared roll per part from `randomVariance` (`[-variance, +variance]`), not three independent per-channel rolls — a per-channel roll produces random hue drift instead of a spread along one hue, which is why `variance` is RGB-only and alpha is never randomized. `physicsFlagsFor(mode)` derives the entity's five physics stage flags from `physicsMode` alone. Module-scoped `particleSurfaceMap` is a zero-origin surface (the same absolute-spawn pattern `player/Model.js` uses), so the public API takes no `surfaceMap` argument. `arcRate` (a cnu `Unit`) and `shrinkFloor` are the two feel constants; they live here rather than in the handler so the frame driver stays pure orchestration.

  **Lifetime classes.** `entity.particle` holds a `particleGroup` instance (non-exported, lowerCamelCase per CASING) carrying an entity back-reference, its stored request, `duration`, `physicsMode`, cloned `spawnOrigin`/`spawnAxis`, `halfAngle`, `startColor`/`endColor`/`variance`, a per-part `offsets` array (one shared r/g/b jitter per part, rolled once at spawn and again on each recycle by `randomVariance`), `total`, `decayStart`, `finished`, `lifespan`, `targetId`. `endColor` is resolved once in the constructor — a clone of `startColor` when the authored `end` is `null` — so the per-frame colour write never branches on "is this constant." `advance(deltaMs, deltaSeconds)` accumulates `total`, integrates motion for `"none"` and applies the arc for `"simple"`, then derives phase from `total` against `duration.holdTimeMs`/`endTimeMs` — numerical and frame-tracked, no wall clock and no `setInterval`. Alpha decay always resolves from the stored base (`displayColor.a = startColor.a * decay`, or `entity.transform.scale` for `"shrink"`), never multiplied, because multiplying compounds and never recovers; RGB is re-written every frame by `writeParticleRgb` from `startColor`/`endColor`/`offsets[i]` regardless of dissipation mode. `expire()` fires at `total >= lifespan` and defaults to `recycle()`, restarting the emission in place.

  Two subclasses extend the base directly (never each other), each overriding exactly one member. `seedingParticleGroup` overrides `seedDue()` — `false` on the base — and only the first group of a `"generator"` request receives it; it emits `amount - 1` siblings at `intervalMs / amount` stride on a monotonic `seedClock` that `recycle()` does not reset. `burstParticleGroup` overrides `expire()` to set `finished = true` instead of recycling, and narrows `lifespan` from `duration.intervalMs` (a recycle cadence, meaningless for a one-shot) to `duration.endTimeMs`; `handlers/game/Level.js` splices finished groups out of the scene. Which class a group gets is a three-way select on `request.mode` (`"generator" | "sibling" | "burst"`) — one field with three states, so the nonsense combination "seeds *and* is one-shot" is unexpressible. `finished` and `lifespan` live on the **base** constructor because the frame driver reads them on every group; a field present only on one subclass would make that read an existence check.
- `NewUI.js` — HTML UI element builder (`UIElement`). Produces DOM element trees consumed by `Render.js`.
- `NewBoss.js` — Boss entity builder. Specializes entity construction for boss characters.
- `NewTerrain.js` — Terrain builder. `BuildTerrains(objects, world, faceTextureStore)` maps each definition through `NewTemplate.js`'s `ResolveObjectSource(definition, "terrain")`, then builds either a single mesh (`source.parts.length === 0` — the original terrain path, one `BuildObject` call with `role: "terrain"`) or, for the first time, a flattened multi-part composition: `buildTerrainParts` composes each part's world transform from root + local (`MultiplyVector3` for scale, root position + local position with per-part grounding, root rotation + local rotation), producing one independent mesh per part with id `${objectId}:${partId}` — there is no composite terrain record analogous to `NewObstacle.js`'s merged-collision record; every part is its own mesh in the returned list. Returns `{ terrain, voidTerrain, meshes }` split by `mesh.meta.mode`. Logs the terrain group count (moved here from `NewLevel.js`).
- `NewTemplate.js` — Shared template-reference and repeat-expansion resolver used by `NewTerrain.js`, `NewObstacle.js`, and `NewEntity.js`. Exports `ResolveObjectSource(source, role)` (`role` is `"terrain"` or `"obstacle"`, selecting the matching `builder/templates/` collection) and `ResolveEntitySource(source)` (selects by the ref's `type`: `"character"`, `"enemy"`, or `"projectile"`). Both are passthrough (return the same reference, no clone) when `source.shape !== "template"` — template resolution never touches hand-authored single- or multi-part definitions. For an actual template reference (`shape === "template"`; template-id existence is guaranteed by this point — validated once at the `core/normalize.js` boundary, so lookups here carry no guards), it field-wise clones the instanced template singleton (`Unit`/`UnitVector3.clone()` for spatial data, `structuredClone` for plain subtrees, special-cased tube `primitiveOptions`/decal transforms) so the shared boot-instanced template baseline is never mutated, expands any `repeat`-bearing part (`count` = additional copies beyond the authored part; copy *i* gets `localPosition += i·offset.position`, `localRotation += i·offset.rotation`, `localScale *= offset.scale^i`; copy ids are `${partId}-r${i}`; `parentId` is copied verbatim so children of a repeated part attach to the authored instance, not a specific copy), then merges overrides at two levels — ref-level (`color`/`texture`/`scale`/`collisionShape`/`mode` for objects; `hp`/`collisionOverride`/`rootTransform` for entities) and per-part (keyed on the *authored* part id, so a part override also lands on that part's generated repeat copies) — using null-sentinel precedence (`payload value !== null ? payload : template`). Object refs resolve `dimensions`/`pivot`/`detail`/`destructible`/`hp`/`static`/`nullable` straight from the template's `shared` block (payload cannot override composition/shape). Entity refs preserve `blueprintId`/`id` from the caller and take `type` from the template (the ref's own `type` field is purely the collection selector, not spawned gameplay data).
- `NewVoid.js` — Null-space void wall builder. `BuildVoidWalls(sceneGraph, textureScale, faceTextureStore)` partitions each null-space mesh's faces via `classifyFaces` (AABB overlap + narrowphase tests): embedded faces become renderable void walls, open/touching faces are retained as world-space `Triangle`s (`UnitVector3`, instanced at this boundary). Attaches a per-pair `relations` map onto each null-space entry in place and writes generated face textures directly into `faceTextureStore` — returns nothing. The void wall per-face noise path calls `ResolveNoiseFaceBlueprint` (same helper as mesh per-face), so void walls honor `primary`/`secondary` color overrides. Called post-build by `NewLevel.js`.
- `templates/` — JSON blueprint data, each collection keyed by template/blueprint id: `characters.json`, `enemies.json`, `projectiles.json`, `terrain.json`, `obstacles.json` (entity-shaped and object-shaped templates, resolved via `NewTemplate.js`), `particles.json` (particle types, resolved via `NewParticles.js` — not part of the `shape: "template"` ref system), plus `levels.json` and `textures.json` (unrelated sample/texture data). `player/characters.json` (a separate file in `player/`) is canonicalized alongside these but is not part of the `NewTemplate.js` template-reference system — it backs player spawns, not `shape: "template"` refs. Treated as part of the builder group; `core/normalize.js` may import from here for payload canonicalization (documented exception in MODULE_GROUPS.md). `Instance.js` exports `InstanceEngineTemplates()`, called once by `core/ini.js` at boot: it `structuredClone`s all eight engine-owned template singletons (`player/characters.json`, `textures.json`'s `scatterTypes`, and the six `templates/` collections above) into a `raw` object *before* Unit-instancing them in place, via five private sister functions — `instanceCharacterTemplates` (player), `instanceScatterTemplates`, `instanceObjectTemplates` (terrain/obstacles: instances the `shared` block, then each part via `instanceModelPart` + `instancePartRepeat`, baking the shared texture into any part authored with `texture: null`), `instanceEntityTemplates` (characters/enemies/projectiles: instances `movement`/`velocity`/`model.rootTransform`, then each part), `instanceParticleTemplates` (instances `velocity`, then the single `part` prototype) — sharing `canonicalizePartTransform` and `instanceModelPart` helpers, then returns `{ raw, instanced }`. `instanceModelPart` also canonicalizes an absent `part.particle` to `null` (mirroring how `instancePartRepeat` handles an absent `repeat`), so every part reaching `CloneTemplatePart` carries the key. `raw` feeds `ENGINE.Blueprints.*` (authored shape — degrees, plain `{x,y,z}`); `instanced` is the same singletons mutated in place, read at call-time by `player/Model.js`, `builder/NewScatter.js`, and `NewTemplate.js` (no import-time IIFE anywhere).

## Boundaries
**Called by:** `handlers/` (Level.js, Cutscene.js, and game-layer handlers call builders to construct scene content); `physics/Master.js` imports `UpdateEntityModelFromTransform` from `NewEntity.js` for post-physics model sync. `NewParticles.js` is called by `NewLevel.js` at build time and by `handlers/game/Level.js`'s `updateParticles` at runtime (for seeded siblings); it imports `IsBeyondSimDistance` from `physics/Collision.js`, a same-tier `builder/`→`physics/` import.  
**Calls into:** `math/` (Matrix, Vector3, Utilities, Collision); `physics/Collision.js` (`NewVoid.js` uses `NarrowphaseTest`); `core/` (meta, config). `NewTemplate.js` imports the five `templates/` collections (terrain/obstacles/characters/enemies/projectiles) directly by static JSON import — these are the same boot-instanced singletons `Instance.js` mutates in place, so `NewTemplate.js` always reads post-instancing data.  
**Does not:** Manage persistent state, drive update loops, or write to the DOM or WebGL directly — all output is consumed downstream by `Render.js`.

## Invariants
- Builders are constructors: given scene input data, they produce scene output objects. They do not hold their own persistent state. Callers supply `faceTextureStore` and `geometryCache` stores; builders write into them, but ownership stays with the caller.
- The `sceneGraph` produced by `NewLevel.js` is the authoritative scene representation shared by the renderer and the physics pipeline.
- Non-template definitions are never touched by `NewTemplate.js`'s resolvers — `ResolveObjectSource`/`ResolveEntitySource` return the exact same reference when `shape !== "template"`, so hand-authored single-part and multi-part behavior in `NewTerrain.js`/`NewObstacle.js`/`NewEntity.js` is unchanged by the template system's presence. `repeat` is a template-authoring-only field; it has no payload schema and can never appear on a hand-authored part.
- Null-space data lives in a per-pair `relations` map on each null-space entry (terrain mesh or obstacle record): `relations[relatedObjectId] = { suppressed, openFaces: Triangle[], voidWallMeshes: VoidWallMesh[] }`. `relatedObjectId` is a terrain mesh id or an obstacle *record* id (never a part id); `relations` is always initialized (`{}` at minimum) so readers never guard the container. This replaces the removed `sceneGraph.voidWalls.{terrain,obstacles}` arrays and the removed `suppressedCandidateIds` sets (suppression is now `relations[id].suppressed`).
- Build order in `NewLevel.js` is load-bearing: terrain and obstacles are built first, then `BuildVoidWalls` runs (attaching `relations`, writing face textures into `faceTextureStore`), then an `openFaces` lookup (`Map<defaultObjectId, Triangle[]>`) is assembled from the relations, and only then are scatter batches enqueued. Scatter must run after void walls so it can reject samples over openings — it is no longer enqueued inline during terrain/obstacle construction.
- `faceTextureStore` is a content-addressed plain object (`{}`, keyed by face content signature) created in `NewLevel.js` and threaded through all builders. Builders write into it; `NewLevel.js` stores it as `sceneGraph.pendingFaceTextures`. At runtime spawn, `handlers/game/Level.js` passes the live `textureRegistry` directly as the store so new face textures dedup against already-resident entries without a separate merge step.
- Level-authored particle generators are resolved at build time, not runtime. Any `levelPart` or `levelObject` (and their `templateObjectRef`/`templateEntityRef` per-part equivalents) may carry `particle: { id, position, overrides }`; `NewObject.js` threads it into `mesh.meta.particle` in all four mesh constructors, and `NewLevel.js` sweeps terrain meshes, obstacle records **and entities** after entities are built — three `ParticleGeneratorRequests(carrier, kind)` calls materialized into one list *before* the generate loop, since that loop pushes groups into the same `entities` array it reads from — then calls `GenerateParticles` per request at `transform.position + RotateByEuler(particle.position, transform.rotation)` and pushes the groups into `entities`. `mesh.meta.particle` is a guaranteed key — `null` or a populated object, never absent — on every path that reaches the sweep; the object-template path is covered because `ResolveObjectSource` forwards `particle` and `applyPartOverride` merges the per-part override. Because the sweep runs inside `BuildLevel`, particle textures and geometry ride `faceTextureStore` and `partGeometryCache` on the normal level path.
- `ParticleGeneratorRequests(carrier, kind)` in `NewParticles.js` is the sole authority on how a built carrier becomes generator requests, shared by the level build and `Simulator.Load` so both produce identical target keys and origin math. Entity parts do carry generators — `NewEntity.js:191` forwards `particle` onto the entity-part `BuildObject` source — so a generator on a moving entity part follows it. Runtime-spawned entities are the remaining gap: `SpawnIntoScene` builds their part meshes with `meta.particle` intact but never sweeps them.
- Particle groups are ordinary entities in `sceneGraph.entities`, which is what lets physics mode `"full"` reach the real physics pipeline. `entity.type === "particle"` is the runtime discriminator (`physics/Collision.js` skips particles in `BroadphaseCollectCandidates` so they never obstruct anything, and in `DetectCombatOverlaps`); `"particle"` is deliberately **absent** from `ENTITY_TYPES` in `core/meta.js`, which selects payload schemas rather than runtime behaviour.
- Particle geometry-cache keys are the bare `templateId` with part ids `p0..p4`, so a particle type costs at most 5 `partGeometryCache` entries across every group and layout config. This holds only because per-particle size variation would go through `localScale` (a pose-time multiplier) and never through `dimensions` — the cache key covers neither shape dimensions nor texture colour.
- `physicsMode` is the **sole authority** over a particle's five physics stage flags; templates author no flag bag. `physicsFlagsFor(mode)` derives them and the modes divide labour with the physics pipeline as: `"none"` → all five false and skipped from `ApplyPhysicsPipeline` by `Level.js`, with the tick integrating position directly; `"simple"` → collision only, the tick applying the arc to `entity.velocity.y` while the pipeline integrates and resolves collision; `"full"` → gravity + resistance + collision, the pipeline doing everything and the tick handling lifetime alone.
- The tick may write `entity.transform.position`, `entity.transform.scale`, `part.localTransform.scale` and `part.mesh.displayColor` — all survive the per-frame re-pose. It must **never** write `part.mesh.transform.*`, `part.mesh.worldAabb`, any `entity.collision.*` field, or `mesh.displayTransform` (which is the same object reference as `mesh.transform`); `applyModelPose` and `refreshEntityDerivedState` recompute all of those every frame. Consequently the tick never calls `UpdateEntityModelFromTransform` itself — `syncEntityMeshes` already does, so bounds refresh after a recycle teleport is automatic.
- Shrink scales `entity.transform.scale`, not per-part `localScale`. Because `ComposeTransform` does not scale local positions by parent scale, each particle shrinks in place while the group's spatial spread holds constant — collapsing the group inward would require scaling the local positions too.
- `count` and `amount` are orthogonal. `count` is the size of one emission, already split across several *in-phase* groups because `groupLayouts` caps at 5 parts per entity; `amount` is how many *phase-offset* emissions are alive at once. Continuity of an effect comes from spacing between emissions, never from within one — which is why the performance tier scales `count` and deliberately leaves `amount` alone.
- Particle groups recycle rather than despawn. Nothing removes a particle group from `sceneGraph.entities`, so a level-authored generator's entity count is fixed once its siblings exist: `groupCount(count) × amount`.
- `sceneGraph.partGeometryCache` is a level-scoped `Map` (keyed `blueprintId::partId`) that holds frozen immutable part geometry templates shared by reference across same-blueprint entity instances. It persists on the sceneGraph for the lifetime of the level so runtime spawns reuse already-computed geometry. `handlers/game/Simulator.js` resets it on each `Load` so edited blueprints always rebuild fresh geometry.
- Consumers read the `relations` model directly: `physics/Collision.js`, `handlers/Render.js`, and `handlers/game/Camera.js` iterate `relations → voidWallMeshes` (and `openFaces` for the stencil) instead of the removed flat arrays. The `Render.js` stencil pass also draws open faces (world-space tris, identity model matrix) with a negative `polygonOffset` to suppress coplanar z-fighting.
- A tube node's `localRotation` defines the **tangent at that node** — shared by the connector arriving into it and the connector departing it. It is not the heading of the next segment. A connector is well-conditioned when both of its node tangents sit symmetrically about its chord; when one tangent lies near the chord and the other far off it, the cubic must approach its endpoint from off-axis and the centerline visibly hooks. This is a property of the authored node data, not of the curve evaluator.
- A tube node owns only the connector that **departs** it: `buildTube` iterates `i < nodes.length - 1` and reads `nodes[i].curved` / `nodes[i].smoothness`. The final node departs no connector, so `curved` and `smoothness` authored on it are never read.
- `buildTube` reuses `resolveCylinderSegments(complexity)` (8 / 12 / 16) for two independent purposes: the radial resolution of each ring **and** the number of connector centerline samples. A tight connector is therefore resolved by at most 17 centerline points.
